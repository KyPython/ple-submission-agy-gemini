## Introduction

This specification defines the Stage 1 open-source readiness, permission boundary hardening, multimodal PDF/drawing inspection, and deterministic post-run deliverable verification enhancements for `agy-gemini` (`/Users/ky/physical-engineering/agy-gemini`), the Antigravity CLI (`agy` 1.4.10) harness targeting `google-cloud/gemini-4-argon` on Physical-Engineering's Last Exam (PLE).

In PLE's isolated two-container architecture (`ple-bench/kit/README.md`, `ple-bench/docs/protocol.md`):

- **Serve container:** Runs `serve.py` as an unprivileged user (`uid 1000`) on a read-only root filesystem with `/opt/harness` mounted, `1 GB` writable `/tmp` and `$HOME`, and outbound network traffic restricted by the egress proxy strictly to the declared model API endpoint. `serve.py` spawns `agy -p` with `tools: []` in `task-agent.md` and proxies task operations through `task_mcp.py` and `taskbridge.Relay`.
- **Task container:** Runs completely offline (no network access) with the engineering workspace, CLI tools, and any task-provided Streamable HTTP MCP servers (`session.mcp_servers`).

This specification addresses four production readiness gaps in the `222df50` baseline:
1. **Permission & MCP Boundary Containment:** Tightening serve-container isolation (`SETTINGS["allowNonWorkspaceAccess"]`, blanket `--dangerously-skip-permissions`), validating all dispatch inputs and secrets at `task_mcp.py` / `taskbridge.Relay`, and eliminating unconditional `"eager": true` registration of large task MCP catalogs (~75k input tokens on 264 tools per `README.md`) while preserving non-interactive arbitrary engineering command execution inside the task container.
2. **Multimodal PDF & Binary Drawing Inspection:** Fixing the mismatch where `serve.py` `AGENT` instructs the model to inspect `.pdf` drawings via `mcp_{bridge}_read_file`, while `task_mcp.py` `IMAGE_MAGIC` only recognizes PNG/JPEG/GIF/WEBP and falls back to binary/text rejection on PDFs.
3. **Programmatic Deliverable Verification Gate:** Replacing prompt-only `Deliverable Verification Guardrails` in `serve.py` `AGENT` with a deterministic `$0` post-run verification and bounded `--conversation` repair loop before `solve()` exits.
4. **Stage 1 Open-Source & Evaluation Readiness:** Adding the missing root `Apache-2.0` `LICENSE`, preserving Stage 2 `submission.yaml` configuration and `kit` compliance, keeping `/opt/harness` bundle size well below `2 GiB` (`kit/build.py` `MAX_BUNDLE_BYTES`), and ensuring `$0` offline CI/testability.

### Out of Scope / Non-Goals

- Modifying `ple-bench` evaluation code, `eval/run.py`, or competition graders.
- Invoking Vertex AI or paid commercial LLM APIs, or executing the 29-task dev set (`eval/run.py`) to generate `artifacts/` during offline development or `$0` CI (dev-set artifact generation is a separate Stage 2 gated run).
- Changing PLE serve protocol v1 wire framing (`taskbridge.py` / `ple-bench/docs/protocol.md`) in incompatible ways or enabling public internet access in the task container.
- Blocking legitimate engineering shell commands (`python3`, `unzip`, CAD/BIM/FEA CLIs) in the remote task container via naive shell command-string denylists or interactive approval prompts.
- Editing application source files, build scripts, or tests during this specification phase.

## Requirements

### Requirement 1: Serve-Container vs. Task-Container Permission Scoping (FRNT-1)

**User Story:** As a PLE harness operator, I want `agy` serve-container permissions strictly scoped while preserving headless task-container command execution, so that the model cannot escape into serve-container files/secrets and never hangs on interactive approval prompts.

#### Acceptance Criteria

1. FRNT-1.1 The system SHALL keep `agy`'s built-in serve-container local tools disabled (`tools: []` in `task-agent.md` generated by `serve.py` `configure()`) across all task sessions.
2. FRNT-1.2 The system SHALL configure `agy` in `serve.py` without unrestricted non-workspace serve-container access (`SETTINGS["allowNonWorkspaceAccess"]` set to `False`, or an equivalent scratch-scoped policy) and replace the blanket `--dangerously-skip-permissions` CLI flag with explicit non-interactive policy rules scoping allowed tools strictly to configured MCP bridge and permitted task tools when supported by `agy` 1.4.10.
3. FRNT-1.3 IF `agy` 1.4.10 rejects or lacks granular non-interactive permission controls or attempts to enable serve-container local execution outside the per-task scratch `home` directory THEN the system SHALL fail closed by logging a structured configuration error via `session.log` and raising an explicit startup error rather than silently reverting to unrestricted serve-container bypass.
4. FRNT-1.4 WHILE executing engineering workflows inside the remote Linux task container via `mcp_{bridge}_shell` the system SHALL preserve headless non-interactive execution for arbitrary engineering commands (including `python3`, `unzip`, and CAD/BIM/FEA CLIs) without introducing interactive approval prompts or naive static shell command-string denylists.
5. FRNT-1.5 WHEN offline `$0` boundary tests run authorized task-container MCP operations (`shell`, `read_file`, `write_file`, `edit_file`) through `serve.py` and `task_mcp.py` against a mocked `taskbridge.Relay` and local mock model proxy THEN the system SHALL permit those task-container calls, reject serve-container filesystem escape probes, and terminate cleanly via `taskbridge` `done`.

### Requirement 2: Dispatch-Boundary Validation, Secret Isolation, and Audit Logging (FRNT-2)

**User Story:** As a security-conscious competition maintainer, I want `task_mcp.py` and `taskbridge.Relay` to validate every tool argument, URL, payload limit, and credential boundary, so that malformed inputs cannot trigger protocol violations and serve-container secrets never leak into the task container or tool responses.

#### Acceptance Criteria

1. FRNT-2.1 WHEN `task_mcp.py` receives a `tools/call` request THEN the system SHALL validate the tool name against `HANDLERS` and validate `arguments` as a dictionary conforming to the tool's declared `inputSchema` (rejecting missing required fields, unknown argument keys, non-string/empty/NUL-containing `path` or `command`, and invalid `offset`, `limit`, or `timeout_sec` types) and return a structured MCP `isError: true` text response on rejection without crashing or emitting malformed WebSocket frames.
2. FRNT-2.2 WHEN `task_mcp.py` dispatches requests over `TASK_RELAY_URL` or `taskbridge.Relay` handles local HTTP routes THEN the system SHALL enforce protocol and buffer bounds (`MAX_TEXT`, `MAX_IMAGE`, `MAX_HTTP_BYTES`, `MAX_WRITE_BYTES`, `MAX_BODY`, `MAX_FRAME`, and clamped timeouts in `1..MAX_TIMEOUT_SEC`) and reject malformed or oversized requests locally before transmitting invalid frames to the evaluator WebSocket.
3. FRNT-2.3 WHEN `taskbridge.mcp_allows` evaluates a target `url` against `session.mcp_servers` THEN the system SHALL permit only `http` or `https` URLs with a non-empty host matching a configured server base URL (or valid subpath/query beneath it) and reject disallowed schemes (`file://`, `ftp://`, `javascript:`, `gopher://`), missing hosts, mismatched origins, `.` or `..` segments, encoded slashes/backslashes (`%2f`, `%5c`), literal backslashes, and `;` path parameters.
4. FRNT-2.4 The system SHALL prevent serve-container credentials and internal relay secrets (`GEMINI_API_KEY`, `MODEL_API_KEY`, `MODEL_BASE_URL`, `GOOGLE_GEMINI_BASE_URL`, `TASK_RELAY_URL`, and `Relay.token`) from being passed to `task_mcp.py` tool responses, task-container `exec` payloads, or unhandled tracebacks, scrubbing any matching secret substrings from tool error outputs and relay logs.
5. FRNT-2.5 WHEN `task_mcp.py` handles a `tools/call` or `taskbridge.Relay._mcp` proxies an MCP HTTP request THEN the system SHALL emit a structured audit log entry recording the tool or server name, normalized target path or byte/timeout summary, outcome status, and elapsed duration while omitting raw secrets and full file/body payloads.

### Requirement 3: Task MCP Server & Tool Scoping and Prompt-Token Control (FRNT-3)

**User Story:** As a harness architect, I want `serve.py` to validate task MCP servers and bound eager tool registration, so that only legitimate task MCP tools are exposed and large MCP catalogs (such as 264 tools adding ~75k input tokens) do not bloat every prompt turn.

#### Acceptance Criteria

1. FRNT-3.1 WHEN `serve.py` `configure()` inspects `session.mcp_servers` THEN the system SHALL validate each server descriptor (non-empty `name` free of path-traversal/control characters, `url` passing `taskbridge.mcp_allows`, and bridge server name collision avoided) and skip invalid entries with a logged warning rather than failing task startup.
2. FRNT-3.2 WHEN `serve.py` `configure()` builds `mcp_config.json` THEN the system SHALL filter task-provided MCP tool names through an explicit configurable allowlist/denylist policy (excluding disallowed or name-colliding tools) prior to writing server tool entries.
3. FRNT-3.3 WHEN `serve.py` `configure()` writes `mcp_config.json` THEN the system SHALL register core `{bridge}` tools (`TASK_TOOLS`) with `"eager": true` and bound eager schema injection for external `session.mcp_servers` (either marking external tools non-eager/deferred or enforcing an explicit bounded eager tool cap) so large MCP catalogs do not inject full schemas into every prompt turn.
4. FRNT-3.4 IF `agy` or a downstream client calls a filtered/disallowed task MCP tool or an unregistered server name THEN the system SHALL reject the call deterministically at the policy or `Relay._mcp` boundary and record both registered and filtered/deferred tool counts per server via `session.log`.

### Requirement 4: Multimodal PDF and Binary Drawing Inspection (FRNT-4)

**User Story:** As an engineering agent inspecting structural, civil, electrical, and mechanical drawings, I want `mcp_{bridge}_read_file` to render `.pdf` drawings into native visual images and summarize binary CAD files cleanly, so that `task_mcp.py` matches the visual inspection instructions in `serve.py` `AGENT`.

#### Acceptance Criteria

1. FRNT-4.1 WHEN `task_mcp.read_file` is invoked on a file with a `%PDF-` magic header (or `.pdf` file confirmed as PDF) THEN the system SHALL perform deterministic in-container PDF page rendering via `relay("exec", ...)` and return native MCP `image` content block(s) accompanied by a structured `text` metadata block (container path, total page count, rendered page numbers, rendering DPI/scale, and pagination guidance) instead of returning a binary rejection message or raw PDF byte stream.
2. FRNT-4.2 WHEN `task_mcp.read_file` renders a multi-page PDF without an explicit page selection THEN the system SHALL bound rendering to a deterministic default page cap (`1..MAX_PDF_PAGES`, default `5`) and support an explicit bounded `pages` argument (e.g., `"1-3"` or `"2,4-5"`, capped at `MAX_PDF_PAGES` pages per call) so multi-page documents remain bounded in token and payload size.
3. FRNT-4.3 WHILE rasterizing PDF pages inside the task container the system SHALL enforce `MAX_IMAGE` (`5 MiB`) per rendered page image and keep the combined serialized MCP response safely below `MAX_FRAME` (`16 MiB`) via deterministic DPI stepping, resolution downscaling, or JPEG fallback, even when the source `.pdf` on disk exceeds the `10 MB` single-read protocol limit (`read_result`).
4. FRNT-4.4 IF no supported PDF rasterizer (`pdftoppm`, `mutool`, `gs`, or Python PDF rendering library) is installed in the task container OR the PDF file is corrupt, password-protected, or receives an out-of-range `pages` specification THEN the system SHALL return a graceful, non-crashing actionable MCP text message stating the failure reason and suggested `shell` inspection steps.
5. FRNT-4.5 WHEN `task_mcp.read_file` reads PNG, JPEG, GIF, or WEBP images matching `IMAGE_MAGIC` (with `RIFF`/`WEBP` check at bytes `[8:12]`) or NUL-free UTF-8 text/ASCII CAD files (such as `.txt`, `.csv`, `.py`, ASCII `.dxf`, or `.ifc`) THEN the system SHALL preserve exact existing `IMAGE_MAGIC` native image responses (including `MAX_IMAGE` rejection) and line-numbered text paging (`offset`/`limit`) with zero regressions.
6. FRNT-4.6 IF `task_mcp.read_file` reads a non-PDF binary file containing NUL bytes within its leading 8,192 bytes (such as `.dwg`, `.rvt`, `.zip`, or compiled artifacts) THEN the system SHALL return a deterministic metadata summary (path, byte size, recognized magic signature where applicable, and actionable `shell` inspection hint) without returning raw binary bytes.

### Requirement 5: Programmatic Deliverable Verification Gate (FRNT-5)

**User Story:** As a PLE benchmark competitor, I want `serve.py` to programmatically verify created/modified deliverables inside the task container after `agy` finishes and trigger bounded repair when checks fail, so that zero-byte, missing, or malformed deliverables are caught before submission exits.

#### Acceptance Criteria

1. FRNT-5.1 WHEN `agy` finishes a run with a candidate answer in `serve.py` `solve()` (before exiting `solve()` and sending `done`) THEN the system SHALL run a deterministic `$0` post-run deliverable verification pass inside the task container via `session.exec(...)` without making any paid LLM API call during verification.
2. FRNT-5.2 WHEN collecting candidate deliverables in a task-agnostic manner (without hard-coding task IDs or reading `ple-bench` grader files) THEN the system SHALL inspect container files created or modified via `task_mcp`/workspace changes plus valid output paths referenced in `session.instruction` or `session.final_message`, verifying regular file existence, non-zero byte size (`size > 0`), `.zip` archive integrity (`zipfile.ZipFile.testzip()` / `unzip -t`), and structural syntax validity for `.json`, `.csv`, `.xml`/`.svg`, `.py`, and `.pdf` (`%PDF-` header and `%%EOF` marker) deliverables.
3. FRNT-5.3 IF the verification pass identifies any missing, empty (`0`-byte), corrupt-archive, or syntax-invalid deliverable AND a valid `conversation` ID exists AND `session.time_left()` exceeds `STOP_BEFORE_SEC + REPAIR_RESERVE_SEC` AND bounded repair attempts remain (`repair_count < MAX_REPAIR_ATTEMPTS`) THEN the system SHALL resume `agy` via `--conversation` with a targeted repair prompt listing the exact failing container paths, failed check identifiers, and diagnostic outputs.
4. FRNT-5.4 WHEN all checked deliverables pass OR repair attempts are exhausted OR `session.time_left()` is at or below `STOP_BEFORE_SEC + REPAIR_RESERVE_SEC` OR `session.cancelled` is set THEN the system SHALL log a structured verification summary via `session.log(...)` (reporting checked paths, byte sizes, and pass/fail status), skip further repair attempts, and exit `solve()` cleanly within the protocol shutdown window without falsifying a passing status.
